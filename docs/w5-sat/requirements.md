# Requirements — w5-sat (W5 P2: RQ1 final, RQ2 final, cross-review consistency, paper v0.9)

## Business Need & Goal

Weeks 1–4 produced frozen pilot data (`results/pilot_rq1.csv`, `results/pilot_rq2.csv`, `results/raw/*.json`, 70 runs) and a W4 draft analysis, but no final answers: RQ1 (which ABP encoding / AMO represents the problem better and whether it helps solving), RQ2 (solver ranking) and the paper v0.9 SAT sections are still open. W5 must turn the frozen data into final, reproducible conclusions, prove that code, spec, paper §3 and appendix describe the same thing via an automated consistency check, close the cross-review of P1's exact family, and deliver a placeholder-free paper v0.9 ready for gate G4.

## User Stories

- As P2 (analyst/owner), I want RQ1 answered programmatically from the frozen dataset so that the encoding/AMO conclusion is reproducible and contradictory evidence is recorded verbatim.
- As P2, I want an RQ2 solver ranking by the Protocol's priority order with per-instance sensitivity so that the canonical solver choice is defensible with primary protocol data only.
- As P2, I want an automated consistency checker over code ↔ `docs/sat_spec.md` ↔ paper §3 ↔ appendix so that no claim in the paper drifts from the implementation.
- As P2, I want to re-verify P1's exact-family review requirements R1–R6 at W5 so that SAT vs exact comparison stays fair and documented.
- As the team (P1/P3/reviewer), I want paper v0.9 SAT sections with zero placeholders and all numbers traceable to frozen data so that gate G4 can be checked off.

## Business Rules

- `BR-1`: All RQ1/RQ2 statistics must be computed from the frozen dataset with explicit provenance. Preferred source is `results/runs.csv` if present at run time; otherwise the frozen fallback `results/pilot_rq1.csv` + `results/pilot_rq2.csv` + `results/raw/*.json` is used and the generated report must name the exact source files. — criterion: the generated report's source line names an existing file set; rerunning on the same data yields byte-identical numbers. — OK: report header "Nguồn dữ liệu: `results/pilot_rq1.csv` + `results/pilot_rq2.csv` + `results/raw/*.json`". / BAD: a number in the report that no listed source file can reproduce.
- `BR-2`: RQ1 slice must fix the non-compared axes exactly as W4: one solver (`cadical195` by default), `search_mode ∈ {"", "multi"}`, `symmetry = false`, `warm_start = false`; only `(abp_encoding, amo_encoding)` varies. RQ2 slice must fix `abp_encoding = order`, `amo_encoding = pairwise` with the same control axes; only `solver` varies. — criterion: every row in a slice passes the same `_is_control_row`-style predicate; rows off-slice are excluded. — OK: `pairwise/pairwise__glucose4` row excluded from RQ1 table. / BAD: mixed-solver RQ1 table.
- `BR-3`: The `order/seqcounter` row is a known duplicate CNF of `order/pairwise` (AMO axis is inert for `order`): it must be reported as a consistency check, never as evidence for either AMO encoder, and must be excluded from counterexample-pair mining (existing behavior in `find_smaller_cnf_slower_solve_cases`). — criterion: no case study cites `order/seqcounter` vs `order/pairwise` as an encoding difference. — OK: case study compares `pairwise/seqcounter` vs `order/pairwise`. / BAD: "order/seqcounter has 196,450 clauses so seqcounter is worse".
- `BR-4`: Contradictory results must be recorded verbatim; the narrative must never force "smaller CNF → faster solve" nor its converse. Both directions (smaller-CNF-slower, larger-CNF-faster) are reported with instance names, clause/var counts, statuses and times taken directly from the data. — criterion: every direction claim in the final report cites a concrete run pair present in the frozen CSV/raw data. — OK: "on `randconn24`, `pairwise/seqcounter` has 16,752 clauses but takes 1.414 s vs `order/pairwise` 20,592 clauses at 0.695 s". / BAD: "smaller encodings are generally slower" without a cited pair.
- `BR-5`: RQ2 evidence hierarchy: protocol data is primary evidence; anything outside the frozen runs (e.g. the separate 3 s-limit timeout-path check, or analytical projections) must be labeled as supplementary/anecdotal and never used to reorder the primary ranking. — criterion: the ranking table is computed only from protocol-slice rows; supplementary evidence appears in a clearly marked subsection. — OK: `glucose4` ranks above `cadical195` by OPT→PAR2→memory from the frozen table. / BAD: a solver re-ranked because of an off-protocol manual test.
- `BR-6`: Kissat is permanently excluded with documented technical evidence (`docs/sat_tooling.md` section "Kissat"; `src/sat/backend.py` `PYSAT_KISSAT_FAMILIES`, `src/sat/solve.py` `_validate_solver`): wrong models, silently ignored assumptions, process abort after `add_clause`, no external binary on PATH. No "Kissat: not installed" row may appear in paper tables. — criterion: RQ2 table contains only `glucose4`, `cadical195` (Protocol Core) and `minisat22`, `glucose42` (PySAT baselines); exclusion rationale is one documented paragraph. — OK: table lists 4 solvers + exclusion note. / BAD: a kissat row sourced from a failed run.
- `BR-7`: `MO` status must be described as it actually behaves: the solver never enforces `memory_limit` in-process; `MO` can only arise from an out-of-process `MemoryError` mapping (`src/runner/worker.py`), and official memory caps are enforced by the runner (Protocol §6.3). `pairwise` memory blowup claims at HB scale must be labeled as analytical projections (clause-count arithmetic), not measurements. — criterion: no measured-MO claim for `pairwise/pairwise` in the frozen data; projections carry a "projection" label and show the growth formula. — OK: "AMO pairwise grows as O(n³); projected clause count for n=some HB size exceeds the 12 GiB host cap (projection)". / BAD: "pairwise/pairwise hit MO on randconn40".
- `BR-8`: FEAS rows must be reported as bounds, not near-optimal gaps: `ub = hi − 1` after timeout before any UNSAT is the trivial counting bound `n − 1` (e.g. `lb = 14, ub = 39` on `randconn40`). The paper must not present `gap = 25` as "close to optimum". — criterion: every FEAS discussion states bound semantics. — OK: "ub=39 is the counting bound, not a tight upper bound". / BAD: "the solver got within 25 of the unknown optimum".
- `BR-9`: Consistency-check failures must be enumerated as concrete, fixable findings (file + symbol + mismatch), not a vague "docs may drift". The checker exits non-zero (or reports FAIL) on any mismatch. — criterion: test run reports each violated anchor individually. — OK: "`order.py` `_not_value` q=1/q=n cases do not match appendix A.5 wording". / BAD: "consistency: 3 issues" without locations.
- `BR-10`: Paper v0.9 SAT sections contain zero `TODO`/`TBD`/`FIXME` markers, and every number/figure in them is generated from or manually verified against the frozen dataset with a traceable source (table id in the generated report or raw run id). — criterion: `grep -i "TODO\|TBD\|FIXME"` over the v0.9 SAT sections returns nothing; each table cites its frozen source. — OK: "Table 3 (source: `pilot_rq2.csv`, generated by `analyze_rq1_rq2`)". / BAD: "≈40s (to be confirmed)".
- `BR-11`: Stale `docs/handoff/...` links in W5-touched deliverables must be cleaned: `docs/w2-sat/14-sat-methodology.md` (5 occurrences) and `docs/w2-sat/15-m1-gate-evidence.md` (multiple) must be repointed to the in-repo locations. `docs/sat_spec.md` and `docs/technical_appendix_draft.md` currently contain zero `docs/handoff/` references — the checker verifies this stays true. — criterion: `grep "docs/handoff"` over the four named docs returns no match (or only intentional, documented ones approved by PM). — OK: link updated to `docs/w2-sat/12-test-matrix.md`. / BAD: `docs/handoff/w2-sat/12-test-matrix.md` kept because the file moved in commit `6137bf3`.

## Non-Functional Requirements (NFRs)

- **Reproducibility:** every number in W5 outputs is regenerable by a committed command (e.g. `python -m experiments.w5_final_analysis --out docs/w5-sat/...`) on the frozen data; reruns produce identical results.
- **No-hand-editing of generated docs:** generated reports carry the "generated by ... do not edit by hand" banner, as `docs/w4-sat/23-rq1-rq2-draft-analysis.md` does.
- **Data integrity:** frozen inputs are read-only; the analysis never writes to `results/`.
- **Test coverage:** all new analysis functions (projection, sensitivity, trajectory extraction, consistency checker) have pytest coverage; the suite stays green (`python -m pytest -q`; current baseline 553 passed / 3 skipped).
- **Auditability:** each paper claim traceable to a file + table/row; the trace table (§ → source) pattern of `docs/w2-sat/14-sat-methodology.md` is reused in the v0.9 SAT sections.
- **Performance:** consistency checker and analyses run in seconds on the 70-run frozen dataset (no solver invocations, pure data reading).

## Edge Cases & Contradictions

- **Missing `results/runs.csv`:** the file does not exist today; P3 may deliver it before W5 closes. Behavior: analyzer prefers `runs.csv` when present, else frozen fallback, and states which was used. Contradiction risk: if `runs.csv` arrives mid-W5 and its numbers differ from the pilot CSVs (e.g. official re-runs vs pilot), both results must not be silently mixed — the report must pick one primary source (BR-1) and note the discrepancy. **Open question OQ-1.**
- **All-OPT RQ2 slice:** the frozen RQ2 data has no TO/MO/ERR, so timeout and memory-pressure ranking criteria are vacuous on this subset. Expected behavior: state the limitation explicitly (decided on instances that all finish within 60 s; hard-instance robustness risk accepted at freeze per `docs/canonical_sat_config.md`), do not fabricate stress evidence.
- **Sensitivity on a uniform subset:** the 10 synthetic `randconn*` instances may not span enough density range to support "A wins sparse, B wins dense". Expected behavior: if the frozen data cannot separate solvers, report that finding with the actual density range; never force a winner narrative.
- **`order/pairwise` vs `order/seqcounter` identical rows:** timing differences (23.24 vs 23.12 s) are noise on identical CNFs; must be reported as the expected consistency check, not encoder evidence (BR-3).
- **CaDiCaL budget-loop overshoot:** `t_total` may exceed `time_limit` (72.67 s at a 60 s limit) — reported as an implementation property of the wrapper, not solver slowness; the RQ2 Core comparison caveat must keep this distinction.
- **`pairwise` AMO inside `abp_encoding=pairwise` is a different axis** from AMO for `order`: `seqcounter` trades variables (7,400 at n=50) for clauses (147,500 vs 255,400) and flips winner by n (faster at n=28, slower at n=50). Expected behavior: report per-n, never as a global AMO verdict.
- **Paper file location:** no paper v0.9 document exists yet in `docs/`; ticket 27 must create it (or its SAT-section fragment) at a path the team agrees on. **Open question OQ-2.**
- **Stale-link scope disagreement:** the ticket text lists `docs/technical_appendix_draft.md` and `docs/sat_spec.md` as handoff-link cleanup targets, but both currently contain zero `docs/handoff/` references; the actual stale links are in `docs/w2-sat/14-sat-methodology.md` and `docs/w2-sat/15-m1-gate-evidence.md`. Expected behavior: clean the two files that have links; verify zero in the other two (checker keeps them at zero).
- **Duplicate `order/seqcounter` rows in `pilot_rq1.csv`:** they exist to empirically verify CNF identity; any deduplication in analysis must keep the identity check visible.
